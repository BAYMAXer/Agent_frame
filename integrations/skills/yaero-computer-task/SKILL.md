将有明确目标和完成标准的界面任务交给 Yaero 执行。Yaero 负责规划、定位、操作和验收；你负责保留用户要求、跟踪运行、核对证据并报告结果。

此技能依赖已连接的 Yaero MCP。工具名称可能带宿主添加的前缀；使用宿主实际发现的工具，不把本文中的工具名当作可直接执行的命令。技能文件本身不会连接 MCP。

## 提交任务

1. 首次使用时调用 `get_capabilities()`，确认可用 profile、执行环境和忙闲状态。`configured=true` 表示配置检查通过，不代表模型接口已连通。
2. 在 `task` 中保留准确的目标、对象、网址、文件名、保存位置、完成标准及用户约束。明确必要的上下文，避免用上层对话中的“这个”“刚才那个”代替。将目标交给 Yaero，自行规划的点击步骤通常无需传入。
3. 选择服务端公布的 `profile`。模型服务、API 密钥和执行环境由服务端配置，不在任务参数中传密钥或任意启动命令。
4. 为一次逻辑任务生成唯一 `request_id`（例如 UUID），调用 `start_task(task, request_id, profile, max_steps, timeout_s)`，检查 `ok`。成功时立即保存返回的 `run_id` 和 `request_id`；`ok=false` 时读取 `error.code` 和 `error.message`，不能视为任务已受理。`completion_spec` 默认省略；确需显式验收条件时，先读 [completion-spec.md](references/completion-spec.md)，只使用已说明的字段，不凭空编造验收条件或把期望结果写成证据。

任务范围和已有授权必须沿用用户请求。若需要用户未授权的外部操作，先明确缺失的授权；不要用委派扩大执行范围。

## 跟踪与重试

- 每次工具调用均检查 `ok`，并处理宿主返回的 MCP 错误。按 `poll_after_s` 调用 `get_task(run_id)`，避免快速重复查询。任务运行和清理期间，不使用其他工具控制同一个桌面或浏览器。
- 调用超时不证明任务失败。已有 `run_id` 时先查询该运行；提交响应丢失时，使用相同 `request_id` 和完全相同的参数重试提交。不要用新 ID 立即创建重复任务。
- `desktop_busy` 表示本次没有启动新任务，等环境释放后再提交。`request_conflict` 表示这个请求 ID 已对应不同参数，应先找回原运行并核对提交内容。不要取消其他任务来腾出环境。
- 配置错误、环境不可用或持续失败时，报告服务端给出的原因。只有已理解原因并有明确修正时才重试；重复的失败不应无限重提。若操作可能已产生外部效果，先核实实际状态再决定是否重试。

## 验收与交付

- `starting` 和 `running` 表示仍在执行。`completed`、`failed`、`cancelled`、`timed_out`、`interrupted` 是终态，进入终态后调用 `get_result(run_id)`。受理成功、进程退出、步骤结束和操作模型的自述都不等于任务验收通过。
- 结合 `success`、`termination_reason`、`verification` 和实际产物报告结果。保留确定性核查与模型核查的区别；证据缺失或验收未通过时，说明已完成部分和仍未满足的要求。
- 下载路径属于 MCP 执行机器。只有自己能够访问该路径或已通过宿主的文件传输机制取得文件，才可声称已将文件交付给用户。
- `artifacts` 提供运行目录内文件及验收记录中已通过的下载文件的路径和大小，不直接传输文件。下载项的 `evidence.status_at_run_end`、`sha256_at_run_end` 是任务结束时的记录；列出文件只确认它当前仍存在，不代表重新核验了内容。仅按需通过已有的文件访问或传输能力读取实际返回的路径，不要猜测路径，也不要将完整截图和轨迹反复塞入上下文。

## 停止

用户要求停止本次任务时，调用 `cancel_task(run_id)`，继续查询直到确认终态。报告取消结果及可能已经发生的操作；取消不能撤销已完成的外部效果。
