## 下载修复及验证

PDF 链接的执行沿用已经连接的 Chrome 页面，不再通过 Python `requests` 访问外网。`browser_download.py` 在最终文档响应阶段保留浏览器原始响应体，将内联 PDF 转为附件下载；代理、证书信任、Cookie 和重定向均由 Chrome 处理。该机制使用 [Chrome Fetch 协议](https://raw.githubusercontent.com/ChromeDevTools/devtools-protocol/master/pdl/domains/Fetch.pdl)中响应阶段省略 body 时保留原始响应体的行为。

通过当前页面的 frame ID、最终响应 URL 和下载 GUID 对应下载事件，文件先写入独立临时目录。只有收到完成事件、实际文件非空且大小与浏览器收到的字节数一致、PDF 文件头正确，才发布文件并记录完成证据。HTML 错误页、取消、空文件、异常大小、无效 PDF 均不算完成。缓存重新检查文件头与本次记录的大小；文件名限制在配置目录内，已有文件保留并使用后缀。

等待下载和响应头同时受单步共享预算及下载自身 90 秒预算约束。超时会取消本次 GUID 并停止未完成导航；只删除本次文件，其他标签页在同一浏览器上下文中产生的文件保留。

真实 Windows Chrome 的本地集成验证覆盖四种场景：

- 禁用 Python HTTP 请求，验证内联 PDF、重定向、会话 Cookie、缓存以及不覆盖已有文件；
- 在 Chrome 私有上下文中配置本地 HTTP 代理，下载一个直接 DNS 无法解析的 `.invalid` 地址，证明传输经过浏览器代理；
- 服务端发送部分文件后停滞，验证共享超时能够终止传输并清理未完成文件；
- 通过完整 AX 快照的 PDF 节点执行精确点击，验证复用当前 CDP 连接而不会嵌套启动 Playwright。

以上验证未调用远端决策模型，也未在提供归档的另一台 Windows 上重跑原任务。那台机器需要更新代码后再运行；下载依赖受管 Chrome 本身能够访问目标文件站点。
